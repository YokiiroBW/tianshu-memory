# TS-302：有来源的对象名称用于后续更正绑定

本任务在 `codex/ts-302-memory-q20` 从 `9f55361bdaa51f83e2df46a0d756cf82fa7fadcb` 追加实现。交付仅为隔离本地候选；未合入 main、推送或部署。Companion `031b9206d519026f1ca6b2ebb56cb9f4d0365575` 及 TS299 保持冻结，由协调者统一集成和验收。

## 问题与变更

已有对象可以用当前消息中的描述绑定，但已保存的明确名称尚未参与绑定。合成案例先保存“透明杯子叫弦月”和旧位置，再说“我后来只把弦月挪到了餐桌”，原实现因名称不等于旧描述而拒绝更正；去掉模型提供的对象 ID 又会另建对象。新实现复用 `fact_entities.resolve` 的同 scope 扫描和既有名称、来源验证能力，将有效的明确 name/title 属性值作为精确名称候选，使合法更正沿同一对象和原属性键更新。

只有名称规范化后精确相等、同 scope/kind、current、时间有效、未被替代且无条件/否定的命名事实进入额外来源检查。候选再经既有 `eligible_groups` 检查完整组、来源及投影，并用 `fact_labels.positive_source` 验证命名原文。多个对象同名仍拒绝，模型提供的 ID 不代替唯一性证明。普通描述匹配保持原有规则；仅少量匹配的名称候选执行分批数据库读取，没有新增名称表、缓存、迁移、依赖或合同。

实际修改为一个运行模块及原有实体、存储测试文件。没有改 `fact_labels.py`、配置、日常 Gemini、媒体功能或挂载。
