## 目标与实现

项目错题是本项目内的有版本对象：触发条件、症状、原因、修正、实际验证、明确的适用范围（平台/语言/框架/适用/排除）与**当前来源证据**。`lesson_record` / `lesson_revise` / `lesson_retire` 走 `KnowledgeApplication` 的同一配置授权、同一 Store 事务和同一证据核对；`lesson_query` 定向检索，`lesson_recover` 给三层短包的当前两层，`lesson_check` 在复用前校验。

总经验**只能由持有独立 `promote` 权限的操作者显式批准**：至少两个不同项目各贡献一条当前错题证据，调用者必须同时有权读取这些项目；模型判断、聊天回执、同项目重复日志、自动日志抓取都不构成晋升依据。全局只保存操作者显式确认可共享的摘要（标题/规则/适用/排除/反例/复核时间）与受保护的引用，不复制项目私密正文或文件路径。

失效是读取时推导，不做后台改写：来源错题被修订/废弃、来源文件被修改/删除、来源文档出现新版本或被墓碑、来源项目主动撤出（`experience_withdraw`）、来源项目被撤权，都让条目变为 `superseded`/`stale_source`/`withdrawn`/`unavailable`，不再返回且旧缓存 `check` 立即失效。撤销（`experience_revoke`）另发新版本并标记 `revoked`。

权限模型：10 个新操作各有操作名权限，`experience_promote` 额外要求 `promote`，`experience_query`/`experience_check`/`experience_revoke`/`experience_withdraw` 额外要求 `review`。`evidence` 中每个 `project_id` 必须在调用者 `projects` 内，否则在读取任何项目数据之前失败关闭——既不泄露项目存在性，也不允许"读取无权项目来凑证据"。

## 迁移与检查点

错题与总经验表属于同一可选域：全新库由 `migrate` 一步安装；已有 TS-080 资料库用新命令 `migrate-lessons --backup` 显式升级。五张新权威表全部带 `source_revision` 触发器；缺少 `lessons_schema` 时所有新操作以 `dependency_unavailable` 失败关闭。不重建或覆盖 schema 3 检查点，旧库恢复仍被 guard 拒绝；备份路径必须不存在且与库/检查点不同。

## 事务边界（共享变更，已跑完整产品检查）

沿用并统一了 TS-080 修正后的两段流程为**三段**，使来源 I/O 与共享写锁彻底分离：

1. **捕获（事务内，零 I/O）**：授权、登记、项目修订、目标版本、幂等结果，并记录每个被引用文件期望的内容哈希。
2. **外部（事务外）**：导入抓取来源；查询/恢复/检查/写回的每个证据文件在此读取并双次校验；`lesson_recover`/`lesson_check`/`experience_promote` 的多项目来源也在此读取。
3. **提交（短事务）**：重读授权与登记，原子复核项目修订、版本与幂等结果，只依据第 2 段结果判定证据是否当前。

本轮的共享改动同时修掉了 TS-080 遗留问题：项目 `query`/`recover`/`check`/`write_state` 的**预览段曾在事务内读文件**，会把慢来源的 I/O 放进共享写锁内（`tests/test_knowledge_concurrency.py` 六项因此从通过变为超时）。现在捕获段完全不碰文件系统，外部段统一读取。

## 验收返修（2026-09-15）

协调者对首轮 HEAD `d796211` 判 `changes_requested`（记录 `docs/development/reviews/DSH-round2-2026-09-15.md`，诊断脚本 `.runtime/acceptance-2026-09-15/review-probes.py TS-081`），两条均已修复并新增正式回归：

### P1 经验读取未检查当前来源有效性

**原行为（已复现）**：两个项目有效资料→各自错题→批准经验→替换 `alpha/notes.md`，`experience_query` 仍返回该经验且 `effect=live`。原因是 `ExperienceBook.effect`/`_content_hash` 只读历史 `knowledge_versions` 的 hash，没有复用当前文档版本、墓碑与当前文件校验。

**修改**：
- `SourceContext.lesson()`（`src/tianshu_memory/lessons.py`）改为用当前文件哈希计算错题指纹，并核对调用方给出的 `hash`；`current_hash()` 拒绝墓碑/替换/不可用文档与已变化的文件。`SourceContext` 现在直接持有 phase reader，因此 phase 1 仍然零 I/O。
- `ExperienceBook.effect/status/check/query` 接收 `application`、`sources` 与 `phase`，复用同一 `LessonBook.lesson_view` 当前证据校验，所以查询与检查结论一致；新增独立判定：错题已修订/废弃 → `superseded`，文档墓碑/文件变化 → `stale_source`，项目修订移动 → `unavailable`。
- 读取路径仍然三段：捕获（登记每个证据文件的期望哈希，无 I/O）→ 外部（事务外读取并双次校验）→ 提交（按第 2 段结果推导 `effect`）。`tests/test_lessons_concurrency.py` 新增两项，验证经验查询/检查在慢文件读取期间不占用共享写锁，且中间文件变化一律报 `stale_source`。

### P2 隐藏证据的检索命中仍可被观察

**原行为（已复现）**：无权读取全部来源的条目仍进入候选，然后被计入 `omissions=["unavailable_source"]`：命中返回 1 项遗漏，随机词返回 0 项，形成关键词命中差异；无权条目还参与排名与预算，可能挤占合法候选。

**修改**：范围过滤下推到 SQL（`experience_query` 的 `NOT EXISTS … project_id NOT IN (SELECT value FROM json_each(?))`），在排名、预算与遗漏统计之前执行。无权条目完全不是候选：不出现、不产生 `omissions`、不挤占合法候选。调用者有权读取全部来源但已失效的条目仍在 `omissions` 中说明真实原因（`stale_source`/`superseded`/`withdrawn`/`revoked`），这是对可见数据的说明而不是泄露。

### 回归

`tests/test_lessons.py` 新增 7 项：当前文件替换、文档新版本导入、文档删除墓碑、来源项目撤权、无权条目不影响遗漏/排名/预算、无权且已失效条目零可观察差异、有权失效给出真实原因。`tests/test_lessons_concurrency.py` 新增 4 项（经验查询/检查两参数各两项：慢读取不占写锁、读取间隙撤权失败关闭）与既有"读取期间文件变化"扩展。既有断言按新语义更新：无权条目不再产生 `unavailable_source`，可见的主动撤出报告 `withdrawn`。
