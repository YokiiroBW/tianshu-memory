## 公共装配接口

```python
tianshu_memory.app.configured_app(
    config_path=None, *, internal_clients=None, storage_environ=None,
    diagnostics=None, log_directory=None, diagnostics_contract=None,
    diagnostics_environ=None,
)
tianshu_memory.app.runtime_app(
    config_path, contract_path, *, internal_clients=None, storage_environ=None,
    diagnostics=None, log_directory=None, diagnostics_environ=None,
)
tianshu_memory.knowledge_http.runtime_app(
    config_path, contract_path=None, *, client, port, authorities=None,
    internal_clients=None, storage_environ=None, diagnostics=None,
    log_directory=None, diagnostics_environ=None,
)
```

三者返回原 FastAPI 应用，不启动 Uvicorn 或监听端口。Knowledge CLI 复用提取后的公共 factory。
`configured_app()` 无显式路径时仍保留原环境变量入口；显式路径不再依赖轮换进程环境。

`internal_clients` 是受信宿主提供的 **逻辑 owner → 零参数新 SyncTransport 工厂**，例如
`{"platform": lambda: exchange.sync_transport("platform")}`。每个 HTTPX client generation 独立拥有其
transport；可在模块 register 前创建，实际请求由 exchange 核验固定目标/origin。同步调用仍来自现有
worker；不能从宿主 loop 线程直接执行同步 transport。不按 URL、Host 或凭据猜目标，不伪造 TLS。

| 现有调用方 | 明确目标 |
| --- | --- |
| SourceTransport 的 `core` 来源 | `companion` |
| SourceTransport 的 `platform` 来源 | `platform` |
| Authenticator 当前配置的 issuer | 对应的显式 issuer owner |
| PlatformVerifier、context PlatformProofs、actor `actor_check` | `platform` |
| actor source producer | 合同中的显式 producer owner |
| RetrievalTransport | `gateway` |

未注入目标继续原真实网络路径；Chat Audit、外部资产服务等不因地址相似被重定向。复用原 OwnerHttpPool
的连接代际、租用和关闭；每次仍读取当前配置、token、权限及来源证明。显式 CA 的外部信任与换代规则保留。

`storage_environ=None` 保留原环境行为，传映射（包括空映射）时业务 Store、actor Store、Knowledge
每代 live config registration，以及 ProbeConfig/SelectedDatabase 都使用该映射。Knowledge 不固定
一份 StorageOptions，也不缓存权限或来源。未修改数据库格式、SQL、Store 线程属性或 SourceAuthority FIFO。

`log_directory` 显式覆盖本模块日志目录，目录沿原行为必须已存在；`diagnostics` 可注入原 Diagnostics。
`diagnostics_environ` 同时用于日志配置环境与诊断 token 查找；空映射不会回读宿主的 Platform token。
工厂创建的 writer 由应用 lifespan 关闭；注入的 writer 由其 Assembly/宿主关闭。

## 原探针与宿主生命周期

`runtime_app` 保留 `app.state.probe_settings(assembly)`，返回带独立 storage 环境的原 ProbeConfig。
工厂本身不新装 `/health` 路由；宿主复用原
`server_runtime.build_assembly(service, build_app, *, config_path, contract_path, binding,
probe_settings=None, diagnostics=None, log_directory=None, diagnostics_environ=None)`
即可安装原诊断 middleware、网络边界和 read-only probes，无需启动 Site。
返回原 Assembly，应用在 `.app`，诊断在 `.diagnostics`；原 `.astarted()`、`.astopping()`、`.astopped()`
分别表示启动完成、停止就绪及最终日志关闭。虚拟 loopback binding 不改变外部 Binding/TLS 约束。

两应用的 `await app.state.drain()` 等待实际已入工作：

- Memory：主 Requests（保留 identity 预留）与 actor 独立 Requests；超时响应不会提前释放工作 lease。
- Knowledge：原四槽主知识执行与 content 独立 Requests；原响应超时后的同步工作完成后才释放槽和资源。
- Memory 启用 retrieval 时：`await app.state.quiesce()` 停止后续 index pass；`drain()` 也停止 producer，
  等当前真实 index_step 和业务 worker，随后 lifespan 才关闭 Gateway backend。未改索引规则与预算。

host 先停止外部 root/producer，再并行 quiesce/drain 各域，**此时 exchange 和窄读 callback 必须仍开放**。
本卡 drain 不拒绝已入工作所需的身份/来源回调，不取消写入或把响应结束当作提交结束。全 host owned work
结束后才关 exchange/application lifespan，再调用 Assembly.astopped()。不能逐 app 先关闭来源池或强制超时
返还槽。未把本卡接点称为五产品宿主 ready 或同 loop 数据库阻塞已隔离；owner loop 隔离由协调者另行装配。
