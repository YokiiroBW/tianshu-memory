# TS-264：PG 短查询、来源同步和写入准备优化

基线 `c4a75d648635b2833c7bf71a74a1100e40688461`；分支
`codex/ts-264-pg-short-write`。本卡是新的隔离实现，没有续写 TS-256，
没有混入未集成 Q17 `7a33c01`。唯一产品工作树为本目录，根记录、共享包、
pin/lock/vendor、生产、NAS、数据库和媒体均未由本执行者修改或访问。

## 实现

- 复用 `Contracts` 与官方 `Registry.crawl` / `Draft202012Validator`，按不可变
  registry 身份及完整引用准备规则，每次仍全量验证当前输入。只对 Draft 2020-12
  本地固定图中唯一 base URI 的静态 `$ref`，通过公开 `Registry.resolver().lookup()`
  复用成功解析的 schema/Resolved，再由官方 `descend` 验证当前实例。相对 `$id`、
  anchor 和 `$ref` 相邻规则保留；任一动态/递归关键字或未知 dialect 使整图回退，
  歧义、外部目标、未知上下文及失败 lookup 使用官方回调，失败不缓存。没有全局
  注册 validator，也未使用私有 resolver 或弃用的 RefResolver。已核验 schema
  树加载后视为冻结；`load_*` 或 registry 替换使准备失效，不支持原地改动冻结
  字典作为热更新入口。缓存没有输入文档、权限结论或来源核验结果。
- PG `_bump` 当前 scope/history/input-history 一次读取，原 `scopes` 写入用
  `UPSERT RETURNING` 取得新版本；同样的两次写入、触发器与历史规则保留，
  产品 SQL 由 7 条变为 3 条。SQLite SQL 保留。
- `_index` 每调用只读取一次完整当前事实及证据文本，用于词与话题分词；下次
  调用重新读取，不跨 DML、事务或操作复用。
- PG `SourceSnapshot` 原 SELECT 一次交给 TS-269 `read_batch`，返回全部已确认
  Cursor 后才生成原映射。调用仍在 CAS 后、首 DML 前；原空键跳过、全库 receipt
  冲突、NULL aliases、跨 actor 负面广播及 epoch 更新保留。协调者已在 `35255f7`
  装配 TS-269 固定 0.1.3；本执行者不修改依赖 pin，也不以兼容 fallback 静默退回逐读。
- PG exact field/item 读取将小集合的 groups/lineage 元数据合为一条语句；超过
  `GROUP_READ_BATCH=512` 的候选只取完整 group 元数据，关闭该语句的 lineage
  扇出，再走原有 512 分批路径，不截断候选。仍复用 `current_many`/fixture
  `_group_current`，所有来源通过后才排队 records 正文和 fact marker；随后批读
  projections 与已启用的事实表，复用 `_units`、`_projections_current` 和
  `FactSnapshot`。最终不完整组的 fact JSON 不提前解码，marker 未启用不读事实表。
  已知版本/零预算短路、后续事务重新核验和 SQLite SQL/惰性读取保持。

`Store` 事务代码、六个新鲜 revision 调用点、锁后新快照、after-checkpoint、
guard-before-commit、CAS 与持久性设置没有改动。没有更改召回语料、预算、BM25、
文件校验、HTTP 生命周期或权限策略。
