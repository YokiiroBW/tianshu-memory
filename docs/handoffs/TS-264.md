# TS-264：PG 短查询、来源同步和写入准备优化

基线 `c4a75d648635b2833c7bf71a74a1100e40688461`；分支
`codex/ts-264-pg-short-write`。本卡是新的隔离实现，没有续写 TS-256，
没有混入未集成 Q17 `7a33c01`。唯一产品工作树为本目录，根记录、共享包、
pin/lock/vendor、生产、NAS、数据库和媒体均未由本执行者修改或访问。

## 实现

- 复用 `Contracts` 与官方 `Registry.crawl` / `Draft202012Validator`，按不可变
  registry 身份及完整引用准备规则，每次仍全量验证当前输入。已核验 schema
  树加载后视为冻结；`load_*` 或 registry 替换使准备失效，不支持原地改动冻结
  字典作为热更新入口。缓存没有输入文档、权限结论或来源核验结果。
- PG `_bump` 当前 scope/history/input-history 一次读取，原 `scopes` 写入用
  `UPSERT RETURNING` 取得新版本；同样的两次写入、触发器与历史规则保留，
  产品 SQL 由 7 条变为 3 条。SQLite SQL 保留。
- `_index` 每调用只读取一次完整当前事实及证据文本，用于词与话题分词；下次
  调用重新读取，不跨 DML、事务或操作复用。
- PG `SourceSnapshot` 原 SELECT 一次交给 TS-269 `read_batch`，返回全部已确认
  Cursor 后才生成原映射。调用仍在 CAS 后、首 DML 前；原空键跳过、全库 receipt
  冲突、NULL aliases、跨 actor 负面广播及 epoch 更新保留。该能力需协调者装配
  TS-269 共享版本；本执行者不修改依赖 pin，也不以兼容 fallback 静默退回逐读。

`Store` 事务代码、六个新鲜 revision 调用点、锁后新快照、after-checkpoint、
guard-before-commit、CAS 与持久性设置没有改动。没有更改召回语料、预算、BM25、
文件校验、HTTP 生命周期或权限策略。

TS-231/tianshu-platform `.runtime/venv/Scripts/python.exe`。测试子进程清除 PG/Redis
环境变量；没有连接 PG/NAS/Redis、真实模型或 QQ。

195 个不同 testcase，无剩余 setup error。两项跳过分别为新增原生 PG bump 专项
和既有 group-profile fixture 限制；既有失败为
`test_confirmation_rejects_mismatched_authority[account-403]` 的 400/403 差异，
此前基线已复现，本卡未修无关行为。

## 协调者需执行的原生 PG 验证

装配 TS-269 固定 wheel 后，至少复验 `test_write_preparation.py` 原生 bump
同事务 DML/rollback 新鲜读取，以及完整 `test_postgres_source_snapshot.py`、
`test_storage_backends.py`、`test_pg_read_performance.py`、`test_pg_followup.py`、
`test_read_setup.py`。尤其确认批中错误全事务失败、七 SELECT 同 CAS/首写边界、
六次 revision 仍完整、全域 receipt 冲突、NULL alias、撤回广播 epoch、旧恢复拒绝、
锁等待后快照、guard 持久化和真实提交顺序。SQLite 写入控制必须计入提交与 guard
fsync，并核对提交后及重开结果，不用已提交 job 的幂等重放代替真实写入。
