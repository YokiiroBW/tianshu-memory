# TS-381 Memory：请求内检索复用与调用关联

基线：线上 R7 `abe78da4293ac679f38d41e13c346ad51c9a5fbf`。本地隔离分支 `codex/chain-domains-20261028`，与 Companion 同号交接成对审阅。没有合入产品 main、推送、部署或访问真实 PG/Redis/账号。

## 实施

- `memory_context/read_v2.execute`：同一请求、同一捕获 retrieval settings 下，完全相同的查询文本只做一次有界 query embedding。不同 query_id、kinds、intent、时间过滤仍分别选取材料并生成证明；缓存只存本次纯计算结果，包含明确失败的预计算，避免在来源边界内补调后端。下一请求重新计算、重新核验来源和权限。8 秒共同预算未延长。
- `read_v2.prepare_query`：facts-only 不再查询 episode 全文索引；episodes-only 不再调用事实词法排序。完整身份、owner/domain 发现、事实目标解析、负证据与最终来源证明保持，未裁剪证明来换速度。
- `diagnostics.correlate_outbound` + `source_http_pool.OwnerHttpPool`：HTTPX 每次实际发送时读取当前诊断 Scope 并写入既有 correlation 头。线程池及 SourceAuthority 的 `copy_context` 子线程保留原执行关联；同一个可复用连接不会保存上个请求 ID。无请求 Scope 的调用获得新的随机 ID。不缓存凭据、授权或响应，不新增记录字段。
- `tests/test_chain_postgres.py` 复用同一正确性用例供协调者在既有隔离 PG 上重放，不更改产品存储或测试框架。

## 链路与必要顺序

| 路径 | 当前实现及边界 | 本次证据 |
| --- | --- | --- |
| HTTP → 身份/origin → 本地绑定 | `chat_requests` 有界准入；`Authenticator` 实时读配置/issuer；service `_authorize` 继续核对账号、scope、期限 | HTTPS 认证、诊断与连接池定向；未放宽认证 |
| v2 query → discovery → 外部向量 → 最终屏障 | query 向量在 Store/source 边界前计算；文档重排离开事务后再复核完整选择，不填补过期材料 | `test_query_vector_boundary`、`test_context_query_selection`、`test_context_bundle_checks` |
| 群/关联 scope → 完整 owner 证明 | `query_domain`、`requirements`、`SourceAuthority` 保留各自完整域；文本相同不会合并授权 | 事实/原话 kind 回归、跨请求撤权、群上下文用例 |
| Memory → Companion facts/window → Platform access → Memory | 来源 FIFO/可重入操作所有权保护全局 revision CAS；外部读取不在 SQL 事务内；Companion facts/window 回调只做原 owner 的同步核对，不反调 Memory | source-order、selected-source、window/消费者联合用例；此所有权锁未盲目拆分 |
| 抽取/写回 → receipt → 修订/遗忘 | 原 Memory 操作/候选账本、先 receipt 再恢复及完整来源核验继续拥有事实 | v2 原话撤回/遗忘、候选恢复与消费者联合用例；没有新记忆账本 |
| Knowledge → capture → 外部文件/URL → serve | `KnowledgeApplication` 在原 Store 上捕获，事务外读取原件，重读配置/权限后校验 revision 再返回；人物身份仍由 Memory/issuer 拥有 | 内容/原件、并发、项目隔离、引用与撤销用例 |
| 关系/好感 | 继续只由 Memory relationships 拥有账本、冻结、衰减和实际结算；关系数据不授予权限 | 本次没有改该领域规则；Companion 同号交接覆盖消费队列修复 |

合成多查询实验的确定结果：同文本的三个不同子查询从三次 embedding 降为一次；下一请求仍再调用一次，撤权后没有任何证据返回。facts-only 的 episode 词法查询为零，episodes-only 的事实排序为零。这里只证明调用数与正确性，不宣称生产 PG 的毫秒提升。

## 实际验证

使用现有 ts345 解释器，加 `verification-r3/vendor` 的 pytest，不安装/改写共享环境。产品 src 显式放入 PYTHONPATH。合同必须使用已经冻结的两套原件：

- 普通 Memory v2/source 检查：`verification-r3/contracts/text-dialogue/v1`。
- Knowledge content：`verification-r3/memory-fixture/contracts/text-dialogue/v1`。本产品原 pin 为 life `ff7cbaf5…`、content `beecd2f7…`；Companion 合同为另一已冻结组合，不得混用或放宽哈希。

结果（多组存在重复节点，不累加成“全套通过”）：

1. `tests/test_query_vector_boundary.py`：50 passed，包含新增两种 audience、向量失败/成功、同文本三子查询、跨请求撤权、facts/episodes 过滤与原有取消/共同预算用例。
2. `tests/test_owner_correlation.py`：1 passed。真实 FastAPI 诊断 Scope → 同步 worker → 两路复制上下文线程 → 同一 HTTPX pool；两个不同请求及非法头均保持隔离，后台调用重新发号，凭据未变。
3. v2 query/context/bundle/group/raw source、source pool/order、verification contexts、Knowledge 并发/引用组：461 passed、61 skipped。首次附带的 Knowledge content 3 failed + 11 setup errors 在任何内容业务前被错误的合同组合拒绝；未修改生产 pin，改用原 native 的 Memory 专属组合后重验如下。
4. `test_knowledge_content.py test_knowledge_content_entry.py test_diagnostics.py test_auth_https.py`：109 passed、3 skipped。覆盖原件版本/哈希、媒体实际解码、独立人物授权及撤销、HTTP/诊断边界。
5. `tests/test_chain_postgres.py`：8 skipped，原因是没有设置显式隔离 PG URL。本地 SQLite 结果不能当 PG 验收。
6. 改动文件 Ruff check、format check、git diff --check 通过。无新增依赖、迁移或共享合同修改。

Companion 当前源码联合验证也运行了实际本产品代码：v2 prepare/verify、source boundary、遗忘、丢失 ACK 与原候选恢复等用例结果见 Companion 的 `docs/handoffs/TS-381.md`。模型、渠道、来源 owner 中未实连的部分都是明确替身。
