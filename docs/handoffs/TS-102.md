## 4. 实现过程中发现并修复的三个真实缺陷

均为**此前不存在**（本卡首次引入该装配路径）的接缝错误，已在本次修复并由测试固定：

1. `build_assembly` 把 `probe_settings` 按位置传给了 `Assembly` 的 `binding` 槽位，导致
   **任何部署装配都必然失败**（`TypeError` → `invalid_configuration`）。
2. `build_assembly` 把 `read_config(raw)` 的结果再次传给 `Diagnostics`（后者自己就会读配置），
   导致**任何部署启动都在建 sink 之前失败**。
3. `Binding.accepts` 只规范化了配置侧、没有规范化请求 `Host`，导致
   `[2001:db8:0:0:0:0:0:1]:8443` 这种同一地址的长写法被误拒。现在两侧走同一套规范化。

另有一处此前遗留：`src/tianshu_memory/cli.py` 在 base 版本缺少
`if __name__ == "__main__": main()`，所以 `python -m tianshu_memory.cli ...`（部署文档与

### 该轮新发现并修复的真实缺陷

1. `Sink.write` 曾把 `sequence` 在共享计数器上自增后再落盘；写线程与调用方并发时会出现重复编号
   （实测同一文件出现 `1,2,3,3,3…`）。现在编号由写线程在 sink 锁内**预留**、落盘完成后才发布，
   文件顺序与编号顺序一致，读取方看到的永远是已落盘的值。
2. 写线程只捕获预期的两种 sink 异常，任何**未预期**异常都会被吞掉并让调用方拿到"未确认但未锁存"
   的判决。现在任何落盘异常都锁存为 `log_unavailable`，该记录标记为失败。
3. 一个**未确认**的写入不会锁存，于是一次慢盘超时只拒绝那一个请求、下一个请求照旧进入——"拒绝"
   因此形同虚设。现在超出确认期限即锁存（写入本身仍不取消、不重发），进程停止接纳新业务。
4. `shutdown` 之后仍会被接受的行会排进一个不再有读者的队列（静默丢失）。现在停止中的进程直接
   拒绝，绝不接受一条写不出去的行。

### 第二轮新发现并修复的真实缺陷（已闭合）

1. **异步接缝遗漏**：`request.started` 已经异步，但鉴权判定仍用同步形式在事件循环里等待；慢盘只延迟
   这一条记录就足以把 10 ms 心跳拖到 257 ms。现在两种形式分开，异步入口一律不等待磁盘。
2. **关闭期句柄双主**：`shutdown` 超时后仍关闭写者正在使用的句柄，既违背单所有者，又让 `close` 成为
   调用方的无界同步 IO。现在句柄只由写者释放。
3. **首次启动竞态**：`Writer.start` 的 check-then-construct 无锁，并发首次事件可产生两个 writer 共写
   一个文件（并因此产生重复编号）。现在启动是原子的，且停止后不可重建。
4. **异步侧无界积压**：把等待交给默认 executor 只是把无界队列从写队列搬到了线程池队列。现在两者由
   同一个上限约束。
5. **内层 IPv6 解析错误**：含冒号即视为无端口，使外层已接受的 `[::1]:8130` 被内层拒绝。现在两侧同一
   套解析与规范化。

### 第四轮新发现并修复的真实缺陷（该轮，已闭合）

除上述两项之外，集中修"完整启动失败/关闭状态块"时又发现并修掉四个真实缺陷：

1. **并发首次启动被误判为启动失败**。`_begin_start` 曾用 `_start_outcome` 同时表达"这次尝试归我"和
   "这次尝试失败了"：第一个调用方在构造线程**之前**就把 outcome 置为 `START_FAILED`，其余 7 个并发调用方
   拿到 `None` 后据此认定失败并执行收尾，把 sink 锁存成 `log_unavailable`——**8 个调用方全部被拒**。
   实测复现：`results == [False] * 8`。现在 `_begin_start` 返回 `(thread, failed)`，`failed` 只描述"这次
   调用拥有那次尝试且尝试失败"，"别人正在启动"是普通答案：既不拒绝、不锁存，也不释放任何东西。
2. **`daemon` 的写法本身就是"启动失败"**。构造后赋 `thread.daemon = True` 在本解释器直接抛
   `RuntimeError`（"cannot set daemon status of active thread"）；构造时传 `daemon=True` 在拒绝守护
   线程的解释器上则抛 `RuntimeError: daemon threads are disabled in this (sub)interpreter`
   （CPython 3.14 起线程默认继承父线程）。两种写法都会让写者**根本不存在**，而 `except BaseException`
   会把这个事实翻译成一个看起来合理的 `log_unavailable`——正是 R2 要消除的那类"看起来正常"的失败。
   反过来"不传 `daemon`"同样有代价：写线程会活过自己的测试并占住段落句柄，实测让 pytest 清理
   basetemp 时抛 `PermissionError: [WinError 32]`（196 个 error，全部以被测环境为原因，不是被测代码
   的失败）。现在按关键字传 `daemon=True` 并把这个选择的理由写进注释：`shutdown` 仍然 join 写者、
   文件仍然由它在退出前自己关闭，守护标志只影响进程退出策略。
3. **`Writer.shutdown` 一次释放两把锁**。把"等启动窗口"拆成独立方法后，该方法在放弃路径上并未重新持锁，
   而调用方仍在 `finally` 里 `self.lock.release()` —— `RuntimeError: release unlocked lock`（并发关停时
   100% 复现）。现在每条路径显式释放，并删掉了那段等待：见 R1，空等对预算有害无益。
4. **`Thread(target, name)` 位置传参是错的**。`Thread.__init__` 的第一个位置参数是保留的 `group`，
   位置传 target 会 `AssertionError: group argument must be None for now` —— 同样被
   `except BaseException` 翻译成"日志不可用"。现在一律关键字传参。

四个缺陷都属于"启动失败"这一块，且都是被本轮新增的失败注入断言抓出来的：只跑既有 265 项无法覆盖它们
（复验的判断成立）。另有两项属于"集中修完整状态块"的必要收口（并发的首次启动不再被误判为失败、
`Writer` 的构造与等待路径不再各自为政），已与本轮的 R1/R2 一起固定，不另计为独立发现。

1. **容量与工作脱钩（R1）**：异步侧原本另有一个 `asyncio.Semaphore` 作为"与写队列同一个上限"的准入。
   它的问题不是超时调得太小，而是它与写者**各算各的**：调用方一取消就归还名额，而记录还在写者手上。
   实测取消 65 个等待后 `semaphore_available == 64`，随即满队列把事件循环阻塞了一整个队列期限。现在
   只有写者自己数得出名额：写入队时占用、写者处理完才归还，异步与同步共用这一个数。
2. **递交在事件循环里等待**：`Writer.submit` 用 `queue.put(timeout=…)`，而 `aemit` 直接在事件循环上调用它，
   所以"满队列"等于"阻塞循环"。现在两侧都是 `put_nowait`：拿不到名额立刻拒绝并锁存，绝不排队等待。
3. **`start`/`shutdown` 交错未定义（R2）**：线程对象在启动前就已可见，关停因此可能 join 一个没启动的
   线程（`RuntimeError`，且此时写者与文件的所有权是模糊的）。
4. **启动早于入队**：修复过程中还发现 `_build` 会先 `writer.start()` 再入队，于是"写者已启动、队列还是空的"
   这个真实顺序存在——此时到达的关停会照常停机并释放 sink，而那条已经被承诺的记录无人来写。现在启动发生在
   入队之后，两者之间不再有可被停机抓住的缝隙。

### 对协调者两个探针的运行结果

两个探针**按原逻辑**在本候选上运行；文件被复制为 `.runtime/r3-*-probe.py`（不覆盖审查者原件），
适配之处只与其自身断言方式有关，已在文件顶部逐条写明：

- **容量探针**（`.runtime/r3-cancel-capacity-probe.py`）：`accepting_at_capacity=false`、
  `call_seconds=0.0`（原实现同一位置实测 > 0.2 s）、`10ms_heartbeat_actual=0.016 s`（原实现 0.251 s）、
  `admitted_at_capacity=64`、`slots_available=0`、`old_semaphore_still_present=false`、`shutdown=true`
  且关停后 `admitted_after=0`。另有两处纯粹是探针自身的调用约定：`Sink.write` 是**关键字**调用，
  补丁必须接受 `line=`/`sequence=`（否则第一次写入抛 `TypeError`、sink 被锁存，测的就不是"被按住的写者"）；
  原探针结尾读取的 `d.writes_in_flight._value` 在本候选中**依设计已不存在**，改为报告 `writer.slots()` 与
  `writer.admitted`，并把"旧名字是否仍可访问"作为一条断言——保留该 semaphore 的候选无法通过。
- **启停探针**（`.runtime/r3-start-stop-probe.py`）：`state_during_window="starting"`、
  `unstarted_join_error=[]`（原实现此处正是那条 `RuntimeError`）、首次记录仍为 `true`、
  `writer_alive_after=false`；第二段 `concurrent_callers=8`、`writers=1`、`verdicts` 8/8 `true`、
  `all_durable=true`、`extra_live_threads=1`。
  原探针第一段断言的是**旧缺陷本身**（关停必须抛那条 `RuntimeError`），而消除该异常正是本轮修复，
  所以改为断言修正后的性质，并把这个 `RuntimeError` 的原文固定在测试里；第二段原本断言 8 个并发调用方
  全部返回 `true`，那是对"8 条记录都在各自期限内落盘"的时间断言而非写者数量的断言（本轮实测确实 8/8 通过，
  也已报告），真正要守的"只有一个写者"保持不变并已断言。
  该探针的 `shutdown_waited_not_joined` 在第四轮之后由 `true` 变为 `false`：这**不是回归**，而是 §6.1 R1
  的既定语义——关停不再把预算花在等待启动窗口上，看到"启动正在内核里"就立刻返回未确认的 `False`。
  真正被守的两条性质仍然成立并已断言：`unstarted_join_error == []`（绝不 join 未启动线程）与
  `first_emit == [true]`（窗口内已入队的记录仍然落盘）。

## 6.3 卡 2 范围补充：第 17 个文件

修复第 4 项时，`src/tianshu_memory/knowledge_http.py` 需要按接口而不是按拼写判断一个 `Host` 是否
是已配置的权威，这要求 `ipaddress` 与 `re` 两个标准库模块。而该入口的架构守卫测试

用 AST 断言限定它只可导入 7 个模块，`ipaddress`/`re` 不在其中——该文件不在原 16 文件白名单内。

处理方式：**没有自行扩大白名单**。先按不新增依赖的方向重写解析（只做规范拼写比较），发现那会
使内层检查比外层绑定更窄（`[0:0:0:0:0:0:0:1]:8130` 被绑定接受、被内层拒绝），正是本轮要修的
那一类不一致；因此上报协调者。协调者随后发布
`docs/development/dsh/TS-102-scope-supplement.md`，**仅批准**该断言把 `ipaddress`/`re` 加入允许
导入集合及相应说明，最大白名单由 16 变为 17。

本交付对该文件的改动**仅此一处**：

- 在允许集合中加入 `ipaddress`、`re`，并写明它们用于"按接口而不是按拼写"判断 `Host`；
- **未**放宽业务、Host/Origin/TLS、领域边界或执行次数断言；
- **未**增加第三项依赖；
- 该补充**不追认**任何其他未授权变动：`git diff --name-only <base> HEAD` 与 17 文件清单逐一
  相等，差集为空（逐文件尺寸与 SHA256 见 `.runtime/dsh-delivery/delivery.json` 与
  `.runtime/dsh-delivery/delivery.md` 的 `allowed_paths_compliance` / `changed_files`）。
  §8 给出本轮的纪律声明。

补充只同步架构测试依赖，**不代表实现已验收**。
