## 3. 登记事件矩阵（全量注册、不采样）

| 事件 | level | 触发点 |
| --- | --- | --- |
| `runtime.starting` | INFO/started | 配置读入、适配器建立后 |
| `runtime.started` | INFO/succeeded | 装配完成、socket 打开前 |
| `runtime.ready` | INFO/succeeded | 就绪判定为真且进程仍在服务（每进程一次） |
| `runtime.start_failed` | ERROR/failed | 装配抛错 |
| `runtime.stopping` / `runtime.stopped` | INFO | 收到自身信号 / 停止完成 |
| `request.started` | INFO/started | 业务请求进入中间件 |
| `request.authenticated` | INFO/succeeded | 身份核验通过 |
| `sync.execute.started` / `sync.execute.completed` | INFO | 业务调用前后（含真实结果） |
| `request.completed` | 按结果 | 请求结束（含 408/断连/5xx） |
| `log.sink_failed` | ERROR/failed | sink 首次写失败（仅 stderr，不入 sink） |

## 4. 实现过程中发现并修复的三个真实缺陷

均为**此前不存在**（本卡首次引入该装配路径）的接缝错误，已在本次修复并由测试固定：

1. `build_assembly` 把 `probe_settings` 按位置传给了 `Assembly` 的 `binding` 槽位，导致
   **任何部署装配都必然失败**（`TypeError` → `invalid_configuration`）。
2. `build_assembly` 把 `read_config(raw)` 的结果再次传给 `Diagnostics`（后者自己就会读配置），
   导致**任何部署启动都在建 sink 之前失败**。
3. `Binding.accepts` 只规范化了配置侧、没有规范化请求 `Host`，导致
   `[2001:db8:0:0:0:0:0:1]:8443` 这种同一地址的长写法被误拒。现在两侧走同一套规范化。

另有一处此前遗留：`src/tianshu_memory/cli.py` 在 base 版本缺少
`if __name__ == "__main__": main()`，所以 `python -m tianshu_memory.cli ...`（部署文档与
`test_knowledge_http_process.py` 使用的方式）**静默退出 0 且什么都不做**。本卡补上该守卫，
与 `knowledge_cli.py` 的既有写法一致。
