## 集中改动

### PG profiles 按阶段读取

`profiles.select` 原来逐组读取 lineage/currentness、records、projection。现在同域 `_eligible` 在 PG 中按现有 `GROUP_READ_BATCH` 分阶段读取：

1. 先核对原 profile scope，并集合读取 lineage，交给已有 `current_groups/current_many` 判定来源 revision/epoch、admission/suppression。
2. 只有来源通过的组才读取 records；原 profile 完整组与 unit 规则集中到 `_units`，继续校验 subject、sharing、category、field、visibility、record identity/version、group identity 及 projection-only sources。
3. 复用已有 projection 查询生成器集合读取，再沿原 `_projections_current` 和 `profiles#unit` 合同逐组确认。

`recall_index` 仅将已存在的 `current_groups`、`projection_queries` 暴露给这个调用方，没有增加通用验证引擎。普通 recall 的规则与来源门槛不变。SQLite 仍逐组懒读；损坏源不会开启正文读取。新增用例还保留早组 schema 错误先于后组畸形正文的行为。

### 同一 operation 的完整 owner 组复用

`verified_scopes` 已经为已观察到的群聊 owner 验证了一批完整组；此前 query 紧接着又读取、验证同批组。现在只在同一持有 Store authority 锁的事务中返回这些已通过的完整组，`group_candidates` 仅复用同时满足以下条件的条目：仍处于本次重新查询的候选窗口，且当前组元数据与刚验证的组完全相同。候选顺序、窗口完整性和名称唯一性域保持。

返回结构增加事务内已验证组，`history` 仅适配内部解包。没有 service/global cache，没有跨 HTTP 或外部排序阶段沿用的证明；外部排序后的 operation 重新同步与验证。RLock、fresh barrier、scope/association/owner checks 和完整组门槛均未削减。

### pending 抽取读取复用已有最终 fresh 事务

`CandidateExtraction.execute(output=None)` 旧链路在 `_content` 的前置 operation、带正文来源快照/授权、后置 fresh operation 后，立即再做一次完全相同 scope/sources/event 的 operation，只读取同 job ledger 与 known facts。

现在把 pending 的 `_completed`、`facts.known` 与 schema 标记读取放进 `_content` 已有的最终 fresh operation。completed receipt 仍优先于新的 pending/hints；显式工具覆盖的 source text 仍先过滤。初始 publisher/actor 授权、正文前后来源门槛与 output 非 None 的提交路径不变。

合成 case 的实际 RPC 序列为两次完整 barrier 加一次含正文快照/授权，共 **8 次** owner RPC；原源码的紧邻第三 barrier 为额外三次。没有用旧授权代替一次仍有 I/O 间隔的 fresh 核验，未减少模型调用或扩大并发/超时参数。

### 计数负载定义

profiles 计数 case 在同一个已授权事务/驱动中比较保留的 scalar 路径和 PG 批读路径，选中 **20或100个完整单记录 profile 组**。每个 fixture 另有建立 reader/原始 projection 的1个基准组，不在计数选择中，因此物理 fixture 合计21或101个 profile 组；它们共用1条合成原始来源，subject、版本、scope、语义和全结果签名一致。这里测往返数，不声称请求耗时同比下降。

- selected records 查询从 N 次到1次；projection 查询从 N 次到1次。
- 来源 admission/suppression 使用现有集合规则1次；所有来源批准后才读取正文。
- 正文行数仍是 N，未减少证据、缩短完整组或提前丢弃成员。
- integrity 覆盖 lineage、成员、scope、subject、sharing、category、field、版本、source kind，以及 projection 缺失/归属/版本，另有源撤回后不读正文与错误顺序用例。

pending 原生节点验证8次 owner RPC 序列、pending 不落 ledger/memory、无效模型提案可重试、完成回执重放；另有 same-job 旧请求中途完成、来源撤回（空/非空提交）、显式工具 source covered 过滤。owner 复用负载为2作者×姓名/宠物共4个完整组：known owner先验2组，后续仅验证剩余2组；每次新 HTTP 请求重新取得来源/权限证明。

## 保留限制

- 全局 SourceAuthority RLock 与各 HTTP 的 fresh 来源核验仍在，网络 owner RTT、服务端排队和模型等待不由这些组件计数证明已解决。没有端到端加速百分比，也没有把 Q19 非受控前后差异归因本代码。
- owner组复用针对同 operation 紧邻的 known-owner内容重读；零预算/history自身仍做完整 fresh 重验，不跨请求共享证明。
- 本号没有修改计划抽取规则。已向 TS298 说明：`known_facts` 是匹配上下文，changed parent plan 的新 group 不会自动继承旧 source，只有 semantic-identical duplicate 会合并旧证据。若新 parent value复制旧地点而其旧源不在本 event，将缺少相应撤回依赖；不能仅凭 prompt 宣称来源已绑定。
- 新增独立 departure/status 子属性可解决同作者唯一旧 plan 尚无该字段的情况，但父 value 若已有具体出发时间，另加“未定”会产生矛盾，当前没有 parent-child失效协议。省略实体名称的 quote 也不能强行继承旧 entity ID。多字段父 plan 更正/证据继承保留为明确边界，本号未擅增 schema、合同或平行记忆实现。
