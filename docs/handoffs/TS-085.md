## 实现要点（与协调者冻结逐条对应）

**工厂与装配。** `create_app(config_path, client, port, *, credential=None, read_timeout=None)`
构建独立 FastAPI app，不复用 `app.py`。`knowledge_cli serve --client --credential-env --port`
只做装配：端口必填、无默认值、无 host 选项，`uvicorn.run(app, host="127.0.0.1", ...)`。
`access_log=False`，因此请求行与 `Authorization` 不入日志。

**身份与授权。** 身份只来自启动参数；`Authorization: Bearer` 的值原样作为 `execute` 的
credential，请求体/query/header 都不能指定身份（多一个字段即 422 `invalid_input`）。
凭据经 `Credential` 每次请求重新读环境变量，轮换或清空无需重启即生效；启动时若该变量缺失或
短于 16 字符则拒绝启动（`missing_service_credential`，退出码 1），不进入「看起来活着但每个请求
都 401」的状态。未新增 token 数据库、账号映射、Platform resolve 适配器，也没有复制任何授权判断。

**每请求新建应用实例。** `application()` 在每个请求内返回
`KnowledgeApplication(config_path)`，只调用公共 `execute`。`app.state` 只放固定 client、
`Credential`、活动槽计数与测试观察点，不放应用实例、项目或请求体。领域实例会改写自身
project/client/权限/域标志，跨请求复用会把上一个请求的授权项目泄漏给下一个请求；AST 用例断言
`app.state.application` 不存在、且模块整体只出现一次 `execute` 公共调用。

**准入与时限。** 读体+执行共用一个 10 秒 deadline；活动 execute 最多 4 个，满载**立即** 503
`overloaded`，不建等待队列。槽用普通整数计数（`claim_slot`/`release_slot`，只在事件循环里改），
而不是带等待队列的信号量：策略是「拒绝」而不是「排队」，且 Python 3.14 的 `Semaphore` 没有
非阻塞获取。

**槽的释放点是本次实现里最要紧的一处。** 响应结束（含 408 超时、断连）**不释放槽**：只有那次
同步调用真正返回时才释放。`run_operation` 用 `asyncio.wait_for(asyncio.shield(work))`，并把
释放放在 `finally` 里判断——`work.done()` 就地释放，否则挂 `add_done_callback`，回调里取回结果
（避免「exception never retrieved」）后再释放。这块在写完单测时暴露过一个真实缺陷：最初版本在
`finally` 里无条件 `release_slot()`，于是「响应超时」等于「释放槽」，一次 408 就能让进程同时跑
超过 4 个写事务，正是卡里点名禁止的「无界」。用例
`test_timeout_does_not_free_the_slot_or_cancel_the_operation` 现固定断言超时后
`app.state.active == 1`（那条调用仍在跑），释放并完成后才为 0。

**不声称取消、不自动重试。** 408/503 只描述传输层。进行中的领域调用不会被取消，也不回滚；
重试靠领域自己的幂等账本：用同一份完整请求重放得到 `replayed: true`，或用 `note_status` 读回。
入口不重试写操作、不发新 `dedupe`。

**错误信封。** 固定 `{"status":"failed","code":"<稳定码>"}`。401 缺/错 Bearer；
408/413/415 分别是时限、超限、媒体类型或非 allowlist 操作；503 是满载与依赖不可用。
**其余一切「读懂但拒绝」都是 422 + 原码**，包括请求体形状不合规（`invalid_input`）与全部领域
拒绝。400 只留给 authority 判定（`invalid_host`、`browser_origin_refused`）。这样 4xx 的语义
集合里不再同时存在「请求没读懂」和「读懂了但拒绝」两种 400，调用方只读 `code` 即可。未知路径
404 `not_found`、错误方法 405 `method_not_allowed`，形状相同。所有响应（含错误）带 `no-store`
+ `nosniff` + `no-referrer`。

**authority 与界面面。** Host 白名单是 `127.0.0.1`/`localhost` 加本进程那一个端口（`/health`
同样检查）；浏览器 `Origin`/`Sec-Fetch-*` 一律 400；无 CORS 预检、无 cookie 接口、不读
`X-Forwarded-*`；OpenAPI/docs/redoc 关闭。

**依赖失败。** `sqlite3.Error`/`OSError`/`ValueError`/`ImportError` → 503
`dependency_unavailable`，只给稳定码不给路径/SQL。这里刻意**不**捕获 `TypeError`/
`AttributeError`/`KeyError` 一类本模块自身缺陷：把自身 bug 报成依赖故障会把它藏起来。

## 与任务卡字面的偏差（3 处，均已在上文与产品文档写明）

1. **`serve` 多一个必填 `--credential-env`。** 卡只写了 `--client --port`（第 17、76 行）。仅凭
   `--client` 无法把凭据喂给 `execute`，而卡同时要求「Bearer 值直接作为既有 `credential`」与
   「不新增 token 数据库」。因此沿用既有 CLI/MCP 的 `--credential-env` 惯例（`knowledge_cli.py`
   已有该参数），并把「该变量缺失则拒绝启动」作为失败关闭项。卡未禁止新增参数，也没有可替代的
   凭据来源。
2. **400 不再承担「请求体形状错误」。** 冻结条件写「传输错误 400/413/415/503」。实现里 400 只留给
   Host/Origin 两种 authority 判定，请求体形状错误归入 422 `invalid_input`，理由见上文；否则
   `{"code":"invalid_input"}` 在线上既可能来自传输也可能来自领域（`validate.py` 的
   `integer`/`exact` 用的正是这个码），调用方无法区分。这是对冻结条件语义的收窄，不是放宽。
3. **新增了一个并发观察点 `app.state.observer`。** 它是测试接缝（默认为 `None`，生产路径不经过
   它），只用来把「调用真正在跑」这件事变得确定，避免用 sleep 猜时序；它拿到的是与生产完全相同
   的 `(body, presented, application)`，因此授权、幂等与事务边界仍然真实执行。未改变任何生产
   判定。
