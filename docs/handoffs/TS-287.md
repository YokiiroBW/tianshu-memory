## 根因与变更

Q18 最终冷负例问“阿宁家那只猫叫什么来着？”。当前群只有团子的公开猫“星渡”；
阿宁及其猫“苔灯”在另一人的私聊，不是本次合法候选。
原 `named_owner` 只遍历已经过来源核验的可见姓名，对每个姓名调用精确
`named_reference`。没有可见阿宁时，没有 match/witness，原规则直接保留全部合法群候选。
后续 `Clause.admits` 优先匹配 cat topic，且亲属约束不解析任意人名，星渡因此入选。
模型又以“要是阿宁就是那位”附加无依据的条件关联。

这是姓名关联缺失后回落到普通话题的相关性错误；不是泄漏私聊内容、存储串人，
也不是直接断言星渡属于阿宁。不能通过读取私聊姓名来判断本次问的是谁。

在现有语言模块增加有限的 `explicit_named_reference`，只识别问题自身的明确人称框架：
强框架为 `X家的…`、`X家那/这只…`、英文 `X's …`、
原有 `X(上次/之前)提过/提到过/说起过/说过…`；弱框架为 `X那/这只…`。
它不创建身份、不返回 person ID、不授予 scope，也不把别名猜成另一个人。
`named_owner` 仍以原当前姓名快照、唯一性、完整窗口和完整原组作唯一归属依据；
无当前唯一可见匹配时，明确框架返回空候选/空 witness，不能再泛召回另一人的猫。
即使尚未安装 automatic facts，也不能把这种框架当成已知姓名关联。

原精确姓名路径先于“无匹配”决策，因此已证据化的单字、英文带空格、普通词形姓名
仍按原规则工作，不受未绑定文字框架的消歧排除影响。
姓名 preamble、来源报告时间、报告动词及否定前缀共用原模块常量，
不另建候选过滤器或第二次检索。

新识别排除普通指代/位置及间接转述前缀，避免把“这家/大家/厂家/作家”、
“桌上那只猫”“有人说阿宁……”误当成句首人名。
对象词只对弱框架消歧，保留“红杯子那只猫”的普通对象路径；
强 home/report 不因昵称含猫/咖啡/说字就丢失人物约束。
未绑定“小猫/咖啡/说说”的强框架先返回空，真实姓名见证及同 owner 猫写入后，
同问可以取回完整姓名/目标组及正确 subject。
`X家的/X家那只` 不把“那只家猫/普通家猫”拆成一个人，
人称前缀也不把“我妹妹那只猫”从现有亲属约束改成未知姓名。
引用中的书名、物品名和发言不作为姓名关联；原 quoted literal 检索保留。
原 source-speaker 表示消息来源作者，与宠物的实体拥有者不同；
第二所有者、并列人、否定/假设来源、引文和多句仍不能被删除后泛匹配。

原 full-group/lineage、实际 owner 授权、不同群/私聊/actor 隔离、预算完整适配、
外部 I/O 后 fresh 来源与姓名唯一性重证等路径不变。

## U+200B 的实际影响

协调者的安全存储投影显示 q93 在 statement、conditions、valid_time、event.outing value 中
出现 `周日\u200b下午`；同组真实证据 quote 仍是
“周日下午想去杉月公园，从南门进会方便些吧。”。
插入点在两个完整时间词之间，`下午`约束仍可识别。
`workflow._index → automatic_facts.index_text` 还会索引完整原 quote，
所以不能仅凭格式观察认定召回失败或重写历史数据。

本卡用同样的最小合成业务形状走正常 draft/commit/query，未在 keywords 添加完整时间词：
原 quote 实际提供跨界 bigram“日下”；“周日下午去哪里，从哪进？”和
“杉月公园从哪个门进？”均取回该 record。
返回 statement、conditions、valid_time 仍保留原 U+200B。
这是该样本的零模型 SQLite 回归证明，不是任意零宽字符都无影响的结论。
没有扩展 `domain.terms`、改写名称、重建索引或清洗旧数据。

## PG 候选与后续边界

只读复核 TS285/286 handoff、根完整 PG 报告及正式分母：运行 `06040aa` 与交接
`6d15af8` 的 src tree 相同；两阶段普通/上下文/撤回后召回三轮约改善 9–12%。
但两种写入对照各版本各场景 90 个正式样本，分别从 24.162 到 36.174 ms
（约 +12.013 ms）、58.845 到 89.449 ms（约 +30.604 ms），三轮方向均不利。
两路径有包含关系，不能相加；约 +50% 是各版本三轮 p50 中位数的比值，
不是百人消息链路每次都多 50%，也不是 300 组整体写入。
后台未冻结、客户端 CPU 与 wall 变化不一致、commit 源码/SQL 路径未改，
仍不足以证明差异全部由补丁造成；同样不能据此宣称写入无退步。
按协调者决定，本卡沿 c696 修功能，不采用/合入 PG 候选，也不重做其
prepared_groups/read_batch、增量预算、Knowledge reference 或来源集合写入工作。

这是有限文字框架，不是通用 NER。未知 plain `X的…` 也可能是“桌上的猫/红杯子的名字”，
本批不强猜人物；已知 source-grounded 姓名的 plain 所有格继续支持。
未知 quoted 姓名、角色称呼、位置/指代歧义、弱框架中的对象词别称及复杂间接转述不保证识别；
不能将未覆盖问法冒称已支持，也不能靠更新 oracle 跳过它。
不新增“叫X的那位”等尚未证明的语法体系。
