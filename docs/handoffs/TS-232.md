## 改动与复用

- 保留 SQLite 默认行为；固定依赖 `tianshu-storage==0.1.0`，安装仓库内 `vendor/tianshu_storage-0.1.0-py3-none-any.whl`。wheel SHA256 为 `e7c8ef910a43a5e2d1f426948fe19e4ea3942e1ff0618a35ecfae03bfedc1482`，没有复制公共包源码或引用可变绝对路径。
- Store 统一装配当前后端、主库、角色准入 sidecar、文件根和关闭生命周期。HTTP、独立 Knowledge、CLI/MCP 与显式迁移复用该入口；Knowledge 每次 dispatch 独立拥有连接运行时，并在各阶段重读授权和存储登记，避免并发调用互相关闭。
- 产品原生 `postgres_schema.sql` 与 `postgres.py` 拥有表/索引、BIGINT 序列、JSONB 运算、全文检索、授权临时语料 BM25、变更触发器及旧 SQLite 导入。导入核对转换后的完整行、版本/引用/回执/抑制/消费水位、原件哈希与身份序列，不以数量相等代替完整校验。
- Knowledge 原始字节、完整抽取文本、完整块正文、上传暂存由共享 FileStore 写入不可变文件；SQL 保留 `tianshu-knowledge-file/v1` 引用、跨度、版本/hash、授权与业务文字。可编辑研究笔记/决策、项目状态、记忆/关系、回执/outbox 与检索索引仍在 SQL。取回文件后继续原来的来源新鲜性、证据组、版本与读者授权验证。
- 旧 SQLite Knowledge 文件化前自动保留独占冷备及 guard 副本；PG 原生 schema 接续使用只读 SQLite 快照。显式 PG 迁移的 backup 是 `tianshu-memory-postgresql-backup/v1` 一致性逻辑 JSON，不再备份已经落后的 SQLite。
- PG 写事务使用同 schema 事务 advisory lock + 同步提交，保留“先验证独立 guard、fsync guard、再提交 SQL”的顺序。运行中缺少 metadata/产品 marker 或恢复成 pre-guard schema 不能绕过独立检查点。旧恢复/提交中断仍失败关闭；首次空库另持久预留 authority identity，允许同一次未提交初始化重试。
- 主库 binding 已 ready 后缺失 metadata/逻辑表，以及准入 sidecar 缺失 grants/operations，均拒绝，不能 CREATE 空账本。历史同一物理路径若已有另一服务 pending/active PG 标记，也明确拒绝第二权威。
- 只读探针使用活跃 Store 或共享 `inspect/open_existing`；停止/未装配状态同样不会读取旧 SQLite 冒称 PG 已就绪。Redis 仅识别可选客户端，没有扩大向量缓存或存放权限/账本。

## 限制与接续

- SQLite/PG 检索的精确分数可能不同，均保持当前授权、完整证据组、预算与新鲜性边界。
- 文件先落盘后提交引用，失败可能留下未引用文件；未新增自动 GC。上传 SQL 引用仍按原有效期清空，文件根需要纳入容量与保留管理。
- 激活后不能断线回写 SQLite；PG→SQLite 回切、历史共享库拆分和来源恢复批准均不自动执行。独立 guard 领先时保留失败关闭状态供协调恢复。
- 操作说明为 `docs/storage-backends.md`，部署/备份整合由协调者接续；保留 TS-220/Q13 候选，不改模型配置。
