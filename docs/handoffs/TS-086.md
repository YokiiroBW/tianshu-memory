## 2. 授权与依赖方向

- 两项各需**同名显式 permission**（`document_list`、`document_read`），由既有 `knowledge.clients` 判定。
  `query`/`recover` **不**隐含枚举或直接读取能力。不改任何现有客户端配置、不自动授权、不新增身份路径。
- 授权判定在项目存在性判断之前；未登记项目 → `project_uninitialized`(409)，读操作**从不注册项目**。
- 依赖方向单向：领域 → 窄 `Evidence` 端口（reader/`fresh`）→ 既有来源核验；领域不反向 import HTTP、
  CLI 或 MCP。HTTP 层只多两项 allowlist，不复制授权、版本、幂等或引用校验规则。
- 迁移只由 `knowledge_cli migrate-catalog` 直接调用 `knowledge_catalog_migration.migrate(store,
  backup_path)`；全新库由 `knowledge_migration.migrate` 调用同一个 `install(db)`。**没有**新的
  `Store` 方法，也没有第二份索引定义。

## 6. 与卡片的差异（如实列出）

1. **游标额外绑定 `budget_bytes`。** 卡只点名 `limit`，实现把 `budget_bytes` 一起封进游标（改预算续页
   即 `invalid_cursor`）。理由写在本文件与 `docs/project-knowledge-catalog.md`：一页按一个预算装配，
   就不该被换个预算重放后还声称遵守了它。响应体**不**含 `limit`：它只属于请求与游标绑定。
2. **两条 SQL 使用 `INDEXED BY`。** 卡要求"查询计划前缀 SEARCH、无临时排序"。实测放任 planner 在键集
   从表头附近开始时可能选 `id` 主键再过滤 `project_id`（成本随别的项目增长），因此语句点名索引，并由
   同一次请求内的形状自检兜底（缺失/错形状 → `dependency_unavailable`）。`EXPLAIN QUERY PLAN` 断言因此
   是逐字前缀断言而不是"包含"断言。
3. **`document_read` 读别的项目的 `document_id` 返回 `stale_evidence`（422）而不是 `forbidden`。**
   与本项目域既有证据规则一致（"这份资料不是本项目证据"），且拒绝体不报告该文档是否存在于别处。
4. **迁移命令的失败输出是一行体 + 退出码 1**（`{"status":"failed","code":"dependency_or_input_error"}`），
   不打印原始异常；因此重复升级在命令层看不到 "already applied" 字样，库内状态用元数据与索引自检验证。
