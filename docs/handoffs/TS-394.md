## Implementation and reuse

Existing actor StorageRuntime, seven authority tables, source/context double proof,
actor/caller allowlists, CAS, immutable receipts and independent guard are reused.
No user records/extraction/profile/summary/retrieval/relationships code or schema
was edited. Existing HTTP application/CLI remain the transport and initialization
entry points; no second scheduler, model, dependency or service was added.

- Separate rebuildable inverted index filters actor/local basis/audience/kind and
  expiry before selecting at most 257 candidates per category. It retains old
  relevant records despite unrelated recent traffic. Selected refs still receive
  original remote proofs; age-based fading does not renew retention.
- Source-backed interest tags and bounded current/history projections preserve
  legacy unspecified preferences. Distinct original content/observation identities
  determine support, never response count, repeated reading or self-expression.
- Management listing, source/dependency impact, exact-version correction and true
  actor-copy forgetting use existing platform service credentials. Forgotten
  episode/derived bodies, replacement history and search terms are erased. Body-free
  identity/receipt/suppression evidence prevents reworded and subset-basis late writes.
- Maintenance expires active and historical derived bodies and compacts exact
  redundant payloads. It rotates at most 256 unexpired rows, expires at most the
  caller's limit, and does not advance the content domain version on an idle tick.
  Semantic autobiography compression stays on sourced append_derived/replaces.

## Explicit schema2 → schema3 migration

Stop actor writers, use the existing configured storage backend/namespace, then:

```console
tianshu-memory --config <private-config.json> migrate-actor-memory --backup <new-local-backup.json>
```

The new startup refuses schema2 rather than silently changing production data.
The command records a consistent `actor-memory-backup/v1` JSON snapshot with backend,
the seven table names/column names/all rows, and exact schema2 guard. It uses a new
exclusive file and fsync before DDL. It then installs `actor_search_terms`, scrubs
legacy negative-state actor bodies, rebuilds the index, advances schema/revision and
persists the existing actor guard. No user DB or other logical source is touched.

Capacity is proportional to the serialized seven actor tables, plus the new index
and database transaction/WAL overhead. No production size was measured and no fixed
free-space promise is made. The backup includes historic bodies and remains private.
It is recovery evidence, not an automatically approved restore. Restoring it requires
coordinated actor-only recovery retaining later suppression; copying its old guard
over the live guard would bypass protection and is not a supported rollback.

`actor_search_terms` is the eighth table in the **same** actor-memory/main logical
source; all seven authority table identities remain unchanged. Original 25 logical
bindings remain unchanged. Any deployment TS361 explicit table inventory must add
this rebuildable table and expect actor schema/guard 3. No new registry source,
connection pool identity or user migration is required.
